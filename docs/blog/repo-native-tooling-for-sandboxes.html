Sandboxes favor repo-native tooling

Oct 30, 2026 · 3 min read
#ai#agents#security

Recent incidents involving rogue agents highlight the importance of sandboxing. A common setup is a privileged gatekeeper agent on your host machine whose sole responsibility is to delegate work to restricted peers in sandboxed containers.

This is not watertight, and as the saying goes: if there is a way in, there is a way out, as we shall see. In any case, it is better than nothing at all. Most importantly, it narrows the contact surface with the outside world.

It's political

Sandboxing also makes interactions with agents a pain. Agents without a way to communicate with peers, the gatekeeper, or humans are impractical. The common solution is to relax restrictions with tooling whitelists. This is not only an annoyance from a technical standpoint. In a large corporation, it takes political skill to navigate security departments and corporate machinery.

Repo-native tooling

A way around this is repo-native tooling - tools that work offline with only Git access. They have most of the allowances in place, as agents need Git anyway to deliver code.

If, for instance, the agent control plane is part of the repository, we need fewer gates to the outside. We can use Git as a communication transport and a plain log in a repository as memory persistence.

This simplifies our setup, but there is a problem: our gatekeeper, with access to the outside, can also modify the code. This is a security risk. In fact, the sandbox itself is typically not what fails, but doors left open on purpose.

To address this we can separate the control plane into a workflow repo, and give the gatekeeper read-only access to the code.

Slipping notes under bars

Repo-native tooling does not address the problem of information flow. An important question is who is reached by what information, with what privileges.

Think of it as a drug lord in prison - the cartel is just as lethal as long as he can slip out notes to someone able to act on them, no matter how restricted he is.

The combination of private data, a way out, and untrusted content is called the Lethal Trifecta.

The idea is that we can contain this risk by not giving any agent all three components.

In our setup, the gatekeeper is the only agent that holds all three legs. It has secrets, it has a way out, and it reads untrusted agent notes. As such, we need to make it human supervised.

Our current model still carries some risk: should external stakeholders get access to the control plane, their input would reach the agents unfiltered, and vice versa. We can stop our drug lord from slipping notes to the outside by adding a public issue tracker alongside the internal issue tracker:

Dead drop

Now the gatekeeper, with no write access to the code, reads instructions from stakeholders and puts notes in the dedicated workflow repo. The notes are picked up by sandboxed agents, with code write access. Think of a Cold War dead drop. In return, sandboxed agents drop notes back onto the workflow repository, leaving an audit trail behind. The gatekeeper reads them as untrusted content.

This is starting to look a whole lot like a setup I am running. For me Epiq is the internal issue tracker and agent memory operating as the control plane. It persists an event log in a dedicated repository, tracking work in other repositories, online or offline.

Bunch of colored boxes

One question remains: how do sandboxed agents push code or call a model without holding any secrets? Using something like OpenShell to run sandboxed agents, we can keep secrets out of the sandbox entirely, since they are appended by a proxy layer on requests leaving the sandbox.

This is a lot of colored boxes, so let's not dive deeper. This should be sufficient to illustrate a basic setup that addresses problems with the lethal trifecta, requiring only: a Git repo, a sandbox, and an agent control plane.

Conclusion - repo-native is composable and sandboxable

Using tooling that is repo-native, standalone and distributed allows you to compose a range of setups, depending on organizational needs.

Epiq can manage one, or both, of the two workflow management planes. Agentic workflows weren't on the radar at its inception, 1.5 years ago, but an append-only event log that lives in the repo and travels over Git turns out to integrate easily with sandboxes, providing a way to coordinate without opening another gap in the wall.
